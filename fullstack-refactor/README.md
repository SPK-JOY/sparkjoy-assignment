# Full Stack Refactoring Assignment

## สถานการณ์

คุณเพิ่งเข้ามาร่วมทีมพัฒนาของบริษัทแห่งหนึ่ง บริษัทมีระบบ Blog ภายในที่พนักงานใช้อ่านประกาศและบทความกันอยู่ทุกวัน ระบบนี้ถูกเขียนขึ้นอย่างเร่งรีบโดย Developer คนก่อนซึ่งลาออกไปแล้ว โดยไม่มีเอกสารและไม่มี Test

ระบบยังทำงานได้ตามปกติ แต่ไตรมาสหน้าบริษัทมีแผนจะเพิ่มฟีเจอร์อีกหลายอย่าง เช่น Comment และ Notification ที่ผ่านมาทุกครั้งที่มีคนพยายามแก้โค้ดชุดนี้ มักมีของพังตามมาเสมอ จนไม่มีใครในทีมอยากแตะไฟล์ `server.js`

หัวหน้าทีมจึงมอบหมายให้คุณ **Refactor โค้ดชุดนี้ให้อ่านง่ายและพร้อมต่อยอด** ก่อนที่ฟีเจอร์ใหม่จะเริ่มพัฒนา ภายใต้เงื่อนไขเดียวคือ **ฟีเจอร์เดิมต้องยังทำงานได้ครบ** เพราะพนักงานยังใช้งานระบบนี้อยู่ทุกวัน

โค้ดของระบบดังกล่าวอยู่ใน [`legacy-app/`](legacy-app/)

## โค้ดตั้งต้น

โค้ดทั้งหมดอยู่ใน [`legacy-app/`](legacy-app/)

| ไฟล์         | รายละเอียด                                   |
| ------------ | -------------------------------------------- |
| `server.js`  | โค้ดทั้งระบบ รวมอยู่ในไฟล์เดียว              |
| `posts.json` | ข้อมูล Post จำนวน 200 รายการ                 |
| `package.json` | Dependency มีเพียง Express                 |

วิธีรันโค้ดตั้งต้น

```bash
cd legacy-app
npm install
npm start
# เปิด http://localhost:3000
```

Test Account ที่มีอยู่ในระบบ เช่น `admin` / `admin1234`

### ความสามารถเดิมของระบบ

- Login ผ่านหน้าเว็บ และผ่าน `POST /api/login`
- แสดงรายการ Post พร้อมแบ่งหน้า (หน้าเว็บ `/list` และ `GET /api/posts`)
- ดูรายละเอียด Post (หน้าเว็บ `/view` และ `GET /api/posts/:id`)
- Filter Post ตาม Tag
- ค้นหา Post จาก Title (`GET /api/posts?q=`)
- ดูรายการ Tag ทั้งหมดพร้อมจำนวน (`GET /api/tags`)
- ทุกส่วนยกเว้นหน้า Login ต้องผ่านการ Authentication ก่อน

## Requirements

### 1. Refactor

ปรับปรุงโค้ดให้อ่านง่ายและดูแลต่อได้ โดยมีอิสระเต็มที่ในการ

- แยกไฟล์และจัดโครงสร้างโปรเจกต์ใหม่
- เปลี่ยนชื่อตัวแปร ฟังก์ชัน และ Endpoint ให้สื่อความหมาย
- ลดโค้ดที่ซ้ำซ้อน
- ปรับรูปแบบ Response ของ API ให้สม่ำเสมอ
- เปลี่ยนไปใช้ TypeScript ได้หากต้องการ
- นำ Library หรือ Pattern ที่เหมาะสมเข้ามาช่วยได้

สิ่งเดียวที่ต้องรักษาไว้คือ **ความสามารถเดิมของระบบตามรายการด้านบนต้องยังทำงานได้ครบ**

> ยังคงต้องเป็น Node.js เช่นเดิม แต่จะคง Express ไว้หรือเปลี่ยน Framework ก็ได้ หากอธิบายเหตุผลได้

### 2. Bug และ Security

ในโค้ดตั้งต้นมีปัญหาด้านความปลอดภัยและ Bug ซ่อนอยู่หลายจุด

- หากพบ สามารถแก้ไขได้เลยโดยไม่ถือว่าผิดเงื่อนไข "รักษาความสามารถเดิม"
- ระบุปัญหาที่พบและวิธีแก้ไว้ใน README ด้วย เราสนใจว่าคุณมองเห็นอะไรบ้าง

### 3. README

README ของงานที่ส่งควรประกอบด้วย

- ภาพรวมของสิ่งที่ทำ
- โครงสร้างโปรเจกต์ใหม่ และเหตุผลในการออกแบบ
- รายการปัญหาที่พบในโค้ดเดิม แยกตามประเภท เช่น Readability, Bug, Security, Performance
- สิ่งที่เลือก Refactor และสิ่งที่เลือกไม่ทำ พร้อมเหตุผล
- วิธีติดตั้งและรันโปรเจกต์
- Trade-off หรือข้อจำกัดที่พบระหว่างการพัฒนา
